《赤石 Akaishi》是一款围绕 **赤石（Akaishi）** 展开的科技与生物改造模组。它由两条互相咬合的主线构成：

- **工业线**：赤石矿脉 → 三级材料加工 → 赤能源网络 → 矩阵反应堆 / 聚变堆发电 → 全自动生产线；
- **生命线**：样本采集 → 基因解构 → 器官培育 → 手术移植 → 排异平衡，以身体为代价换取超越凡躯的力量。

两条线共用同一套能量、物流与配置体系：反应堆产物既供电也供养生命机器，器官产出又反哺工业效率。

## 核心系统

### 资源与材料加工

- **赤石矿脉**：主世界 / 深板岩 / 下界 / 末地四种环境，当前仅保留中浓度档，共 4 种矿石
- **三级加工链**：打粉机磨制粉末 → 变化器转化为矿物基底 → 压缩机压制粉末成块；粉末与基底深度参与各级机器、管道与饰品配方
- **赤水晶**：晶洞生成，瑕疵 → 普通 → 完好 → 完美四级母岩，催化器逐级升阶，自动收集器代工采集

### 能量体系

| 层级 | 载体 | 来源 |
| --- | --- | --- |
| 赤能源 | 能量细胞 / 能量管道 | 燃烧赤石晶、精华块；能量发生机、发生器矩阵 |
| 生命能量 | 生命管道 / 储存器 | 聚合转换架构消耗赤能源聚合，更高的能量形态 |
| 燃料 / 等离子体 | 7 种反应堆燃料 → 3 种等离子体 | 液化装置、燃料混合器、能量加工器、聚变聚合器 |

能量逐级跃迁：赤能源 → 下界至纯 / 复合能量 → 七种反应堆燃料 → 衰竭燃料 → 活化液体 → 等离子体，
每条链都有专属机器与闭环回收。

### 多方块结构

| 结构 | 尺寸 | 亮点 |
| --- | --- | --- |
| 反应堆 | 5×5×5 ~ 7×7×7 | 燃料棒 × 散热片；400~700 ℃ 最优产率，超温减产不停机，1000 ℃ 触发 10 秒爆炸倒计时并留下「衰竭区域」 |
| 聚变堆 | 7×7×7 | 温度以百万计（50M 起步），效率框架 × 散热框架 × 燃料框架三向博弈 |
| 矿机 | 9×9×5 镂空塔 | 钻头打出信标光束；速度 / 时运 / 储能升级模块按等级解锁，产物经转口与立柱物品输出口出货 |
| 无线终端 | 5×5×5 | 跨维度传输、区块弱加载、损耗抑制组件 |
| 矩阵 | 3×3×3 / 5×5×5 | 发生器矩阵 45 倍 → 高级 200 倍、提纯矩阵、生命转换矩阵、超级发生器核心 |

### 衰竭区域

反应堆失控的代价：污染等级按 3 的次方区块梯度扩散（泄漏 3 区块 → 爆炸 81 区块），持续 30 小时。
区域内禁生生物、暗紫雾笼罩，草皮枯死、山石腐化，亡灵生灵化为凋零骷髅系 —— 直到衰变净化塔以 10 倍速将其驱散。

### 器官移植与基因

```
样本采集 → 生命分析台解构 → 生命结构台构造 → 培养舱提纯 / 品质升级
         → 培育器施加突变词条 → 手术仓移植 / 摘除
```

- **9 个器官位**：眼、心、肺、脏器、肾、双臂、双腿，各绑定生物来源与品质档位（I~IV）
- **排异机制**：排斥值上限 100，含负面阈值、躯体超载、天敌反噬、日光自燃等代价 —— 移植并非没有成本
- **突变词条**：三档稀有度，良性 vs 畸变双刃剑，词条重铸仪可原位重铸
- **基因强化**：永久药剂吸收基因型，同源器官互为增幅；排异中和剂清洗减轻负担

### 药剂系统

- **永久药剂**：吸收基因型，永久强化同源器官适配
- **突破药剂**：三向临时爆发（均衡 / 狂涌 / 深沉），药剂台调配、药剂库存储

### 无线网络与物流

- **无线网络**：身份卡即钥匙的赤能源无线终端 —— 输入 / 输出口、跨维度传输、区块弱加载、损耗抑制组件，参考 MEK 量子传输，远程供能不再受距离束缚
- **物流管道**：物品（4 级，1~64 个/tick）/ 液体 / 废料 / 等离子体 / 赤能源（4 级）/ 生命能量管道全家族覆盖；废料与等离子按族物理隔离
- **第三方兼容**：物品走 `ITEM_HANDLER`、流体走 `FLUID_HANDLER`，漏斗、MEK 管道、AE2/RS 均可直接对接；方向语义（输入 / 输出槽）由机器自身声明，适配层逐槽遵守，不放宽限制

### 装备与升级

- **赤石装备**：基础属性为下界合金 ×1.25；装备打造器提供 4 点基础升级，升级台解锁高级能力（吸血、击退、移速、防火、防爆、区域破坏、掉落精华等）
- **机器升级**：速度 / 能量升级组件，矿机专用升级模块
- **Curio 饰品**：7 件（饱食、狩猎、采集、防火、防爆、净化、凋零防护）

### 附加内容

- **转基因工厂**：凋零骷髅基因序列 + 缠怨藤 + 凋零玫瑰 → 凋零藤作物体系
- **母神祭坛**：5×5 底座 + 四角柱，NBT 献祭识别与悬浮供奉
- **游戏内手册**：《赤石研究日记》（科技主线）、《生命的奥秘》（器官与药剂）、《基因详解》（全数值查表）
- **JEI 集成**：15 个配方类别全覆盖
- **配置系统**：`config/akaishi-common.toml` 全量数值可调，游戏内界面热重载即时生效

## 架构与实现要点

项目采用 **Architectury** 双模块结构，追求「平台代码尽量薄、逻辑只写一份」：

| 模块 | 职责 |
| --- | --- |
| `common` | 全部游戏逻辑、数据与资源（方块 / 物品 / 方块实体 / 菜单与界面 / 网络包 / 数据生成 / 语言与手册） |
| `forge` | 平台实现：Forge 能力注册、配置规格与界面、事件桥、GameTest 入口 |

**跨平台与依赖倒置**

- 平台相关能力统一下沉为 `api` 包下的接口（能量、流体、物品管道、仓储、安全、价值服务等），
  `common` 只依赖接口，平台实现经 `ServiceHolder` 式入口注入，保证两端行为一致。
- 物流方向语义**唯一真源**是机器自身实现的 `IItemPipeDevice` / `IFluidPipeDevice`：
  机器声明输入 / 输出槽，Forge 能力适配层逐槽遵守，GUI 与自家管道共用同一套判定，不存在第二份口径。
- **能量例外**：赤能源 / 生命能量为自研能量体系，按设计**不对外暴露第三方能量能力**；
  物品与流体则全面开放，可与主流自动化模组混用。

**配置系统闭环**

```
ForgeConfigSpec (COMMON, 带取值范围与中文注释)
      → AkaishiConfigSync.sync()
      → common 侧 ModConfig 的 volatile 字段
      → ConfigSyncS2C 广播（登录 / 热重载后全服同步）
```

- `0` 约定为「不覆盖，使用内置默认」；列表下标对应品质序数或来源组序数，读取端越界自动回退；
- 新增配置项需同时落地三处：配置界面条目、双语 `config.akaishi.*` 键、`toml` 注释；
- 保存即生效，无需重启或重进世界。

**性能与稳定性设计**

- 大表构建分片推进（按时间预算切片），避免首次打开界面时阻塞服务端线程；
- 高频热路径（价值估算、配方索引、可制作判定）全部带指纹缓存，配方表变化即失效；
- 虚拟加工规划设节点 / 批次双闸门，超限直接判定「不可加工」，绝不做无界递归；
- 资源与产物流转全部走「先查后取 + 失败原样回填」纪律，杜绝吞吐过程中的物品复制与丢失。

**数据与资源规范**

- 注册分域（按功能域拆分类），方块 / 物品 / 方块实体 / 创造栏 / JEI / 手册同步落地，
  杜绝「有注册无入口」「有入口无图标」的孤儿数据；
- 语言文件严格双语对齐（当前中文 = 英文 = 1,968 键，零缺失）；
- 开发期自检：`-Dakaishi.gametest=1` 启动服务端后自动核对器官注册（孤儿器官、属性 ↔ 槽位合法性矩阵）与燃料系统，
  `-Dakaishi.gametest.reactor=1` 核对反应堆体系。

## 构建与运行

**环境**：JDK 17（Gradle toolchain 会按 `gradle.properties` 中的路径探测安装位置）

```bash
# 构建（产物在 forge/build/libs/）
./gradlew build

# 仅编译校验（最快的回归手段）
./gradlew :common:compileJava :forge:compileJava

# 启动开发客户端
./gradlew :forge:runClient

# 启动开发服务端 + 开发期自检（属性会由 forge/build.gradle 注入服务端 JVM）
./gradlew -Dakaishi.gametest=1 :forge:runServer

# 反应堆体系自检
./gradlew -Dakaishi.gametest.reactor=1 :forge:runServer
```

> `-Dakaishi.gametest=1` 会在服务端启动后核对**器官注册完整性**（孤儿器官、采集分组、
> 属性 ↔ 槽位合法性矩阵）与燃料系统链路；断言失败会直接打印在日志中，便于脚本化回归。

## 工程约定

面向贡献者与后续维护的核心约定（也是本仓库长期坚持的规范）：

1. **注册 · 生效 · 可见，三段缺一即视为未完成**
   任何新增数据/机制都必须同时具备：可获取入口（合成 / 掉落 / 机器产出）、平台生效层真正消费、
   双语语言键与展示位（创造栏 / JEI / 手册）。缺任一段都会产生「看得到用不到」的坏数据。
2. **单一真源**
   物流方向只认机器的 `IItemPipeDevice` / `IFluidPipeDevice`；配置只认 `AkaishiConfig`；
   库存口径只认 `CraftLibrary`。适配层永远不放宽上层语义。
3. **双语零差异**
   `zh_cn.json` 与 `en_us.json` 键集合必须完全一致，提交前做一次差异核对。
4. **版本对齐**
   严格按 MC 1.20.1 的实际 API 实现，不照搬新版本教程（例如效果集合不得使用 `Map` 返回值、
   不得使用 `MobEffects.JUMP_BOOST`）。
5. **变更即验证**
   改动后至少保证 `:common:compileJava` 与 `:forge:compileJava` 退出码为 0；
   界面与建模类改动以实机截图复核「所见即所得」。

## FAQ

**Q：为什么赤能源 / 生命能量不能被其他模组的能量管道识别？**
A：这是刻意设计。两种能量是自研体系，不对外暴露 Forge 能量能力；需要与外部交换时请走物品 / 流体形态的载体（燃料棒、储罐等），
这部分能力是完整开放的。

**Q：为什么 Cloth Config 和 Curios 是硬依赖？**
A：前者是游戏内配置界面的基础（本模组全量数值均可在界面内调整），后者提供饰品槽位，二者缺失时模组无法正常加载。

**Q：数值平衡能改吗？**
A：可以。`config/akaishi-common.toml` 覆盖倍率、损耗、缓冲容量等全量数值，
游戏内界面调整保存即生效；配置项中 `0` 统一表示「使用内置默认值」。

**Q：手册里的数值和实际不一致怎么办？**
A：以配置文件与游戏内实测为准。手册用于讲清机制与查表，配置改动不会回写手册内容。
